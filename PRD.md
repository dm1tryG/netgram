# NetGram — PRD (v0, на утверждение)

Локальная Next.js-прила: **безопасный, scoped read-only доступ AI к выбранным Telegram-чатам**. Не «аккаунт, живущий за тебя», а «узкий безопасный интерфейс агента к тому, что ты явно разрешил». Обоснование дизайна и safety-логика — \[\[side-project-ideas\]\] (раздел 2).

## Зачем (goal)

Дать AI/CLI читать нужные TG-чаты (ресёрч болей/лидов, дайджест, память) **без** передачи ему всего аккаунта. Allowlist enforced на сервере → агент физически не может запросить не-разрешённый чат.

## Главный принцип

- **Read по умолчанию**. Write — отдельное, явно включаемое разрешение per-chat (см. ниже), не глобальное.
- **Scoped allowlist** — агент видит только выбранные чаты; на запись — только те, где отдельно включён Write.
- **Local-first** — сессия и данные лежат локально, наружу ничего не торчит.

> Обновление (2026-07-12): изначальный MVP был read-only. По прямому запросу
> добавлено **per-chat Write-разрешение** — один селектор уровня доступа на
> чат (Off / Read / Write; Write всегда включает Read) с реальной отправкой
> сообщений через API/CLI. Это
> осознанный отход от исходного non-goal «никакой отправки в MVP» — см.
> Security model ниже.

## Архитектура

- **Next.js** (UI + API routes) на `localhost:<PORT>`.
- **GramJS** (`telegram` npm) — MTProto user-сессия (аналог Telethon для Node).
- **Сессия**: строка сессии GramJS хранится локально (файл/`.env`/1Password), gitignored. Если сессия есть — логин пропускается.
- **Allowlist** — список chat_id, которым разрешён доступ; проверяется в API-слое ДО обращения к GramJS.
- **CLI (**`netgram`**)** — ходит на localhost API, НЕ имеет прямого доступа к GramJS/аккаунту. Вся власть у сервера, CLI — тонкий клиент.

```
[CLI netgram] ──HTTP──> [Next.js API (allowlist gate)] ──> [GramJS session] ──> Telegram
                              ↑
                        [Next.js UI: логин + настройки чатов]
```

## Фичи MVP (по твоим 3 пунктам + safety)

1. **Локальный сервер** — `npm run dev`, открывается `localhost:<PORT>`.
2. **Auth / сессия**:
   - Если валидная сессия уже лежит → сразу в приложение.
   - Иначе — экран логина: phone → код (→ 2FA-пароль если включён) → сессия сохраняется локально.
3. **Настройки → список чатов**: подтягивается список всех диалогов, есть поиск по названию; на каждом чате один селектор уровня доступа — **Off / Read / Write** (Write включает Read). Сохраняется в allowlist (`{ [chatId]: { read, write } }`, `write: true` всегда влечёт `read: true`).
4. **Scoped API**:
   - `GET /api/chats` — список чатов + флаги `read`/`write` (для UI).
   - `GET /api/allowed` — только чаты с `read: true`.
   - `GET /api/chats/:id/messages?limit=` — сообщения, **только если `read` включён**, иначе 403.
   - `POST /api/chats/:id/send` — отправка сообщения, **только если `write` включён**, иначе 403.
5. **CLI** `netgram` — обёртка над этими эндпоинтами (`netgram chats`, `netgram read <id>`, `netgram send <id> <text>`), чтобы Claude/агент ходил через неё.

## Security model

- Allowlist проверяется **на сервере**, не на клиенте → CLI/агент не обойдёт.
- Read и Write — независимые флаги per-chat; включение Read не даёт Write и наоборот.
- Сессия/креды — только локально, gitignore, не в ваулт-историю.
- Честный нюанс: на уровне Telegram API user-сессия физически видит всё; сэндбокс обеспечивает ИНСТРУМЕНТ (сам отказывает вне allowlist/вне нужного флага), не крипта. Для agent-safety достаточно (агент получает узкий capability, не ключи).
- Write — реальная отправка, без draft/approve-шага в API. Ответственность за то, какие чаты получают Write, на человеке (селектор уровня в UI). Разработка/тестирование send-функциональности — только на собственном self-чате (`284637542`, «Dmitrii Galkin»), не на реальных людях/группах.

## Non-goals (MVP)

- Аналитика (боли/лиды/дайджест/память) — **фаза 2**, после ядра доступа.
- Личные/чувствительные чаты — по умолчанию НЕ в allowlist (ни Read, ни Write).
- Мультиюзер/хостинг — только local-first, один пользователь (ты).
